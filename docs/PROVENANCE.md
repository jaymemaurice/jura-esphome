# Research provenance, contributions and confidence

## Why this document exists

The goal is to avoid presenting community knowledge as new discovery, or
presenting observations on one machine as universal. **Pre-existing knowledge,
locally observed discoveries, project implementation and hypotheses are four
separate categories**. Dates and versions in the old research notes are the
project's historical labels, not evidence of worldwide priority.

## Pre-existing publicly documented work (not originally discovered here)

1. **Protocol JURA community/wiki**: pioneering Jura service-connector,
   serial/framing information and early command catalogues. Historical wiki
   links may be unavailable; the earlier references remain preserved by other
   projects. This repository does not claim invention of the service protocol.
2. **hn/jura-coffee-machine** (Jura Impressa E65): an ESP8266 HTTP gateway,
   `TY:`, `AN:`, `RT:`/`RE:` command examples and a software serial encoder.
   The accompanying Perl script documents `RR:` RAM-page reads and the
   9600/8N1 connection. <https://github.com/hn/jura-coffee-machine>
3. **Q42/coffeehack**: serial access and historical EEPROM comparisons for a
   Jura machine. <https://github.com/Q42/coffeehack>
4. **Jutta-Proto/protocol-cpp**: the published UART framing and command
   structures for other Jura generations; notes the distinction between the
   original V1 protocol and newer implementations.
   <https://github.com/Jutta-Proto/protocol-cpp>
5. **Community home-automation integrations** also preceded this work. The
   present component should not be described as the first Jura automation
   implementation. These projects should not be assumed to share the same
   EEPROM layouts or serial transport across firmware generations.

**Pre-existing items:** UART service-port concept, command/response case
convention, `TY`, `AN`, `FA`, `RE`, `RT`, `RR` command families, V1 4:1
obfuscation and use of an ESP microcontroller as a bridge. We implement or
extend these ideas; we did not originate them.

## Evidence generated by this project on the reference machine

Reference target recorded in captures as `655 M V01.12` (X9-era Jura).
The following are specifically attributed to **this project's controlled
655 M experiments**; they should not be generalized without new captures.

| Result | Evidence and confidence | Primary internal reference |
|---|---|---|
| Complete observed `RT:00..F0` range, 256 16-bit EEPROM words; `RR:00..F0` 256 RAM bytes | Direct successful page captures on this target; **observed**, not a claim of physical chip limits | [EEPROM_MAP](research/EEPROM_MAP.md), [DISCOVERY_NOTES](research/DISCOVERY_NOTES.md) |
| Ten physical recipe/action records at EEPROM words `D4..FB`, 4 words each | Controlled `EC` function-byte replacement (`0C02` → `0502`) changed slot 7 Macchiato to Cappuccino; **confirmed on 655 M** | [EEPROM_MAP](research/EEPROM_MAP.md) |
| High byte of first record word carries function code; separate physical `FA` slot code | Multiple function trials; **confirmed for mapped codes on 655 M** | [EEPROM_MAP](research/EEPROM_MAP.md), [COUNTER_MAP](research/COUNTER_MAP.md) |
| Pot (`08`), Ristretto (`09`), Double Ristretto (`0A`), Latte/Milk variants, hold functions and locked/unsafe codes | User-observed controlled menu/product reactions; **specific to this target**. Unsafe `1A..1C` deliberately excluded | [EEPROM_MAP](research/EEPROM_MAP.md) |
| Scheduling word `25`, auto-off `26`, power-off `28`, weekday mask `57` | Controlled UI/EEPROM changes; **confirmed for tested settings** | [EEPROM_MAP](research/EEPROM_MAP.md) |
| Lifetime and user counters | Controlled increment and some write/readback verification; **per-field confidence varies** | [COUNTER_MAP](research/COUNTER_MAP.md) |
| RAM `D7` active Recipe 1–8 lamp mask and `D6` flashing subset | Compared real button illumination across RAM captures; **confirmed on this target** | [historical README](history/README-original-v22.20.9.md) |
| RAM `16`, `44`, `58` power/awake probes | Repeated correlated transitions; **candidate/consensus**, not hardware-defined authoritative state | [RAM_CANDIDATES](research/RAM_CANDIDATES.md) |
| Temperature and clock/timer-related RAM pairs | Correlation and perturbation analysis; many **unproven** units, endianness and offsets | [RAM_CANDIDATES](research/RAM_CANDIDATES.md), [CLOCK_TIMER_RAM_DISCOVERY](research/CLOCK_TIMER_RAM_DISCOVERY.md) |

**Important qualifiers:** "Confirmed" means confirmed for the explicitly
recorded firmware, conditions and tests—not all related models. "Strongly
inferred" is not independently experimentally toggled. "Candidate" is
correlation without established semantic meaning. Unknown fields remain
unknown even when their captured value is 0 or `FFFF`.

## Engineering work done in this repository / conversation

The current ESPHome C++/Python implementation, native-API entities, bounded
nonblocking UART scheduler, ten-slot recipe editor, EEPROM read/modify/write
verification and safety gates, RAM/EEPROM discovery modes, ESP8266 resource
optimizations, syslog integration, web console, live-memory parser, decoded
bitfield tables, table-linked FA actions, and regression tests were developed
and iterated in this **project workflow**. It incorporates and builds on
previous Jura control concepts; it is not asserted to be the first implementation.

This work involved human-supplied hardware observations, captures, decisions,
review and ESPHome compile/error reports, together with extensive
**AI-assisted drafting, programming, debugging and documentation using OpenAI
ChatGPT models**. The machine-specific facts below are based on reported
experiments and recorded project notes, not on the model independently
operating the machine. A passing source/test suite does not constitute an
independent hardware verification by the AI.

The very earliest codebase/legacy YAML in the project was supplied as an
existing starting point. **Its complete original authorship and any incorporated
third-party code have not been independently audited here.** The repository
retains the existing GPLv3 license; before public publication, the maintainer
should check imported snippets, source headers and attribution history. Links
to existing protocol repositories are credits for prior information, not a
claim that their source files were copied into this repo.

## Evidence checklist for new models

For each new mapping, store: model and firmware string (`TY:`), electrical
interface and adapter, exact machine state, pre/post full or relevant
addressed reads, timestamp, one operator action, repetition with a control
trial, expected response and counterevidence, and a confidence label. Avoid
publicly sharing credentials, LAN IPs, machine identifiers or unredacted
personal usage counters. Use the [field notes template](EVIDENCE_TEMPLATE.md)
and [reverse-engineering guide](REVERSE_ENGINEERING_GUIDE.md).

## Public sample data policy

The GitLab-prepared distribution **does not include the user's unredacted
complete EEPROM/RAM snapshot**. The browser's bundled data is synthetic,
with illustrative programming fields retained and counters/unknown regions
zeroed; the memory-map appendix redacts original per-address values for
private or unidentified fields. The underlying experimenter can preserve
original full captures in a private evidence archive if desired.
